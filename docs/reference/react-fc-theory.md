## 에이전트와 도구 (슬라이드 3~8, 18~23)
- 에이전트 = 목표를 받으면 스스로 계획하고 도구를 쓰고 결과를 보고 다시 판단하는 프로그램 = **두뇌(LLM) + 도구 + 반복 루프**.
- **고정 파이프라인이 나은 경우**(순서가 정해진 일, 예: `query_rag`)와 **에이전트가 값어치를 하는 경우**(몇 번·어떤 순서로 도구를 쓸지 모를 때, 질문마다 필요한 도구가 다를 때)를 구분한다. 에이전트 과용은 비용 폭탄의 흔한 원인.
- 도구 = LLM이 요청할 수 있게 **이름과 설명을 붙인 함수**. 네 조각: 이름 / 설명 / 인자 스키마 / 본문+반환. **모델에게 넘어가는 건 이름·설명·인자 스키마뿐**이고 본문은 못 본다.
- 도구 종류: 읽기(조회) / 계산·변환 / **쓰기(행동, 되돌릴 수 있나가 기준)** / 다른 에이전트 / 메모리.
- 도구를 쓰는 이유: LLM이 못 해서가 아니라 **믿고 맡기고 확인할 수 있어야 해서**. 확률 ≠ 보장(큰 수 계산·날짜), 모델이 모르는 데이터(오늘 날짜, 우리 DB).
- **"에이전트는 도구의 이름과 설명만 보고 고른다."** 설명이 모호하면 도구 선택이 흔들린다.
  - 좋은 설명 공식: 무엇을 다루는지 / 언제 쓰는지 / **언제 쓰지 말아야 하는지**.
  - 설계 5원칙: 새 동료에게 말하듯 / 이름에 접두사 / 도구는 적게·역할은 뚜렷하게 / 반환은 모델이 쓸 정보만 / 실제 질문으로 돌려 보고 고치기.
- 도구가 돌려준 결과도 **못 믿을 입력**(간접 프롬프트 인젝션: 문서·웹 속 숨은 지시). 쓰기 도구일수록 승인 장치.

## 1부 ReAct (슬라이드 11~38) — 참고용
- 생각(Thought) → 행동(Action + Action Input) → 관찰(Observation)을 **글자로** 반복, 출구는 `Final Answer`. LLM은 글자만 쓰고 **실행은 우리 코드**가 한다.
- 세 부품: ① 프롬프트(역할+도구 목록+형식+가드레일+scratchpad) ② 파서(정규식) ③ 루프(`run_react`).
- `stop`: 모델이 가짜 Observation을 지어 쓰기 전에 끊는다. **프롬프트의 "직접 쓰지 마세요"는 부탁, stop은 차단.**
- scratchpad = 메모장이 곧 기억. 길어질수록 비용·속도 문제.
- **안전장치 3대**: `max_iters`(반복 상한) / 오류는 예외가 아니라 **관찰(문장)** 로 / 관찰 길이 제한(`OBS_MAX`).
- 디버깅 순서: 로그를 위에서부터 — 도구 선택 오류(→ 도구 설명), 검색어 오류(→ 프롬프트), 검색 실패(→ RAG 튜닝), 해석 실패(→ 더 큰 모델·프롬프트). "모델이 나빠서"라고 결론 내리기 전에.
- 범위 밖 질문: 도구 없이 "모른다"가 이상적. 그럴듯하게 답하면 환각. **"OO 관련만 답할 수 있어요"** 문장을 프롬프트에 두고 그 동작을 평가 세트에.

## 2부 펑션 콜링 (슬라이드 39~58)
- **핵심 두 문장:** ① 모델은 함수를 실행하지 않는다 — "이 함수를 이 인자로 불러 줘"라는 요청서(JSON)만 쓴다. ② 실행은 우리 코드가 하고, 결과를 `tool` 메시지로 돌려주면 모델이 최종 답을 쓴다.
- ReAct와 비교: 호출 표현 글자 → JSON / 읽는 법 정규식 → 파서 필요 없음 / 형식 위반 잦음 → 드묾 / 도구 설명 프롬프트 글 → `tools=` 스키마 / 기억 scratchpad 문자열 → **messages 리스트**(system/user/assistant/tool).
- **"손으로 한 바퀴"** = 설명서 전달 → 요청 받기 → 우리가 실행 → 결과 돌려주기. `run_agent`도 교재 `create_agent`도 이 세 단계. 막히면 여기로 내려와서 모델이 뭘 돌려주는지 본다.
- 종료 조건: ReAct는 `Final Answer`, 펑션 콜링은 **"요청이 없음"**(모델이 글로 답함).
- 로그 `[Function Call]/[Parameters]/[Output]`: **에이전트 버그의 절반은 인자.** `[Output]`에 없는 말을 하면 환각.
- 날짜 함정: 테스트 데이터의 고정 날짜는 시간이 지나면 조용히 깨진다 → 오늘 기준 상대 날짜. LLM은 오늘 날짜를 모르므로 **시스템 프롬프트에 코드가 넣는다.**
- 좋은 도구 체크리스트: 동사+대상 / 인자마다 설명+예시 / 선택 인자는 기본값+생략 시 동작 / 오류는 "다음에 할 일" 문장 / 반환은 ID보다 이름 / 계산·날짜·정확한 조회는 도구에 / 읽기와 쓰기 구분.
- **보안 ① 권한은 코드로**: 프롬프트 규칙은 부탁이다. 모델이 ID를 고르지 못하게 **인자 없는 도구 + 서버 변수**로(OWASP "과도한 에이전시"·"프롬프트 인젝션"의 기본 방어선).
- **보안 ② 되돌릴 수 없으면 사람에게**: `NEED_APPROVAL` + `approve_fn`(HITL). 실서비스에선 `input()` 대신 승인 버튼.
- **도구 위험도 분류**: 읽기 → 자유 / 되돌릴 수 있는 쓰기 → 실행+기록 / 되돌릴 수 없는 쓰기·금전 → 사람 승인 / 타인 데이터 → 코드로 차단(ID 서버 주입). (우리 `.claude/rules/tools.md`의 등급이 이것)
- 개인정보: 도구가 전화·이메일을 그대로 돌려주면 로그에도 남는다 → 마스킹, 로그에 남기지 않기.
- 멀티턴이 되는 이유: 모델에게 기억은 없고 **이력을 통째로 다시 넘기기 때문**. `keep`(최근 N개)이 크면 느려지고 작으면 잊는다. 기억 전략: 최근 N개 / 오래된 것 요약 / 중요한 사실만 따로 저장.

## 핵심 문장 7개 (슬라이드 57, 시험 포인트)
1. LLM은 "말"만 하고 "실행"은 우리 코드가 한다 2. 도구 설명이 에이전트의 눈이다 3. 모델에게 기억은 없다 — 이력이 곧 기억 4. 오류는 예외가 아니라 결과 문장으로 5. 반드시 `max_iters` 상한 6. **권한과 승인은 프롬프트가 아니라 코드로** 7. "LLM이 실제로 본 것"을 보며 디버깅

## 우리 프로젝트에 적용할 점
- 우리 도구 설명에는 "언제 쓰지 말아야 하는지"를 넣는다. 예: `search_health_docs`는 용량·복용 판단 질문에 쓰지 말 것.
- 설명을 쓴 뒤 **질문 20~30개 + 기대 도구**로 평가 세트를 만들어 바꿀 때마다 비교한다(`docs/test-log.md`, 감이 아니라 숫자로).
- 안전장치 3개를 `run_agent`에 모두 둔다: `max_iters`, 오류→tool 메시지, 도구 결과 길이 제한(리포트·검색 결과가 길 때).
- 위험 판정·환자 ID·승인은 "부탁"이 아니라 코드로(절대 원칙 2·3, `NEED_APPROVAL`).
