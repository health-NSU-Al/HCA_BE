- 구성: 정거장 5개 — ① 에이전트가 뭐지? ② 도구 ③ ReAct ④ 펑션 콜링 ⑤ 실무 주의점(날짜·보안·승인).

## 핵심 문장
- 에이전트 = **목표를 받아 도구를 쓰며 반복해서 해결하는 프로그램** = 두뇌(판단) + 손발(도구) + 심장(반복·기억). 핵심 모양은 **판단 → 도구 → 결과 → 판단** 루프.
- **판단이 필요 없으면 에이전트를 쓰지 않는다.** (순서를 안다 vs 순서를 모른다. 예: "매일 9시 날씨 전송", "PDF 항상 3줄 요약"은 에이전트가 필요 없고 "수업 안내를 찾아 계산해 답하기"는 필요하다.)
- 도구 설계: **이름은 동사+대상 / 설명은 3요소(무엇을·언제 쓰나·언제 쓰면 안 되나) / 인자엔 예시 / 에러는 글로 / 출력은 읽기 쉽게.** 이름이 `tool_1`, `tool_2`면 에이전트는 고를 근거가 없다.
- ReAct = 생각 → 행동 → 관찰을 **글자로** 반복. 루프의 출구는 `Final Answer`. 프롬프트 = 역할 + 도구 목록 + 출력 형식 + 주의사항 + 스크래치패드.
- 컨텍스트 윈도우 = 모델의 책상 크기. 넘치면 앞부분이 밀려난다 → 기억은 유한: **최근 것만, 길면 자르고, 필요하면 요약.**
- 안전장치: 지어내면 `stop`, 안 끝나면 `max_iters`, 형식이 틀리면 안내 쪽지로 되돌려 준다.
- 펑션 콜링: ReAct는 글자를 뜯어 해석하고, 펑션 콜링은 **양식의 칸만 읽는다**(JSON). 알려주기 → 요청받기 → 실행·반환(번호와 함께) → 최종 답변. **LLM은 요청하고 실행은 코드가 한다.**

## 확인 퀴즈 (슬라이드 끝)
- O/X: 질문마다 무조건 검색 1번 하는 것이 에이전트다 → X
- Observation 칸을 채우는 것은? → 파이썬 코드 (LLM이 아님)
- 에이전트가 도구를 고르는 근거는? → 이름과 설명
- 같은 도구만 계속 불러서 끝나지 않을 때 안전장치는? → `max_iters`
- O/X: 프롬프트에 "C001만 조회"라고 쓰면 다른 고객 조회가 확실히 막힌다 → X (코드로 막아야 한다)

## 우리 프로젝트에 적용할 점
- "판단이 필요 없는 일은 코드로"가 우리 설계 원칙과 같다. 알림 시각 판단·위험 판정은 코드(그래프·규칙), 대화에서 도구를 고르는 일만 LLM.
