# 참고: AI 에이전트 기초 (수업 1장)

- 출처: `docs/lectures/01_AI에이전트.pdf` (26쪽, 교재 「AI 에이전트 개발 완벽 입문」 1장 요약). 슬라이드 번호는 PDF 쪽 기준.
- 용도: 보고서 "기술 선택 이유"와 발표 때 "왜 에이전트(워크플로 포함)로 만들었나"를 설명할 때 쓴다.

## 에이전트의 정의
- 에이전트 = **상태(State)를 보고 다음 행동을 스스로 선택(Select)하고, 외부 도구로 실행(Act)** 하는 AI 시스템. 챗봇은 입력 1개에 응답 1개로 끝난다.
- 앤드류 응: "에이전트냐 아니냐"가 아니라 **"얼마나 에이전트적인가"** (스펙트럼). LLM이 결정·행동 선택을 직접 할수록 에이전트적이다.

## LLM 앱 자율성 6단계 (그림 1.1)
| 단계 | 이름 | 누가 다음 단계를 정하나 |
|---|---|---|
| 1 | Code | 사람 (그냥 프로그램) |
| 2 | LLM Call | 사람 (한 번 묻고 끝) |
| 3 | Chain | 사람 (프롬프트 여러 개를 코드가 순서대로) |
| 4 | Router | LLM이 분기, 반복 없음 |
| 5 | State Machine | LLM이 **루프를 돌며** 판단 → 에이전트 실행의 시작 |
| 6 | Autonomous | LLM이 수행 범위까지 결정 |
- 경계는 4↔5 사이(반복을 LLM이 결정하는 순간).

## 에이전트의 세 요소 (그림 1.5)
**LLM = 사고, 도구 = 행동, 기억 = 경험.**

## 언제 에이전트가 필요한가 (1.2)
- 에이전트는 만능이 아니다. 정확도가 오르는 대신 **비용과 지연이 늘어난다.**
- 에이전트형이 자연스러운 경우: 단계가 미리 정해지지 않음 / 중간 결과로 다음 행동을 골라야 함 / 예외가 잦음 / 외부 도구·데이터 접근이 필수.
- 단일 호출·RAG·워크플로로 충분한 경우: 단순 조회·질의응답 / 규칙이 반복되는 작업 / 입출력 패턴이 명확.

## 프레임워크·표준
- **LangGraph**: 그래프(순서도)로 워크플로 관리 (교재 4장). **CrewAI**: 역할 분담 팀 에이전트 (5장). **MCP**: 에이전트↔도구·데이터 연결 표준, "AI 앱을 위한 USB-C" (9장). **A2A**: 에이전트↔에이전트 통신 표준.
- 멀티 에이전트 구조 6가지: 계층형 / **사람 개입(HITL)** / 도구 공유 / 순차형 / 중앙 지식베이스(RAG) / 메모리 변환. 단점은 조정·통신 복잡도와 비용(에이전트 수 × 루프 수).

## 우리 프로젝트에 적용할 점
- 우리 구조는 **5단계(루프를 도는 `run_agent`) + 워크플로(LangGraph)** 를 섞은 것이다. 알림 발송·위험 판정은 사람이 정한 규칙(1~3단계에 가까움)으로 고정하고, 대화에서의 도구 선택만 LLM에 맡긴다. → "에이전트는 만능이 아니고, 의료 판정은 코드가 한다"는 설계 이유로 쓴다.
- CrewAI를 안 쓴 이유: 사용자 1명, 에이전트 1개 구조라 멀티 에이전트의 비용·복잡도만 늘어난다(결정사항.md「기술 스택」).
- **HITL(사람 개입)**: 캘린더 등록 승인(`NEED_APPROVAL`)과 재측정 `interrupt`가 해당한다.
- MCP: 가상 측정기 서버 → "나중에 실제 기기 API 서버로 바꿔도 에이전트 코드는 그대로"의 근거.
- 수업 환경(학교 H200 GPU 서버, 공용 conda `dl`, Ollama 로컬 모델, 학생 비용 0원 원칙)은 안내서의 "GPU 서버의 로컬 LLM" 요건의 배경이다. 우리는 Gemini API를 쓰므로 교수님 확인이 필요하다(`docs/requirements.md`).
